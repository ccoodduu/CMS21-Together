# Proposal

## Why

Each client's `OrderGenerator` runs on its own: every player sees a different set of orders with colliding
job ids, two players can accept the same order, nobody else sees the customer car's job, and ending a job
adds the payout only to the finisher's local money, which the next `WorldState` from the server then
overwrites. Orders and jobs are the core co-op loop (ROADMAP row 3), so the server has to own them.

## What Changes

- The server owns the list of open orders and active jobs, assigns job ids, counts down order expiry and
  stores it all in `ModGameState` so it survives a restart and reaches late joiners.
- Orders are still generated by the game, but only on one client that the server elects as the
  "order generator" (no game code on the server). That client hands each new `Job` to the server, which
  stores it and broadcasts it to everyone, including the generator.
- Accept and decline become requests the server approves, so exactly one player can take an order.
  The taker's native `TakeJob` spawns the customer car through the existing `CarSpawnRequest` flow,
  now with `IsJob`/`JobID` filled in.
- Task progress that the car state cannot reproduce (found parts, money spent on parts) is relayed.
- Ending a job is reported once to the server, which applies the payout to shared money and the XP to
  shared exp, removes the job and its car for everyone, and rejects a second finish of the same job.
- The orders window and the car's order tab show the server's list on every client, also after the
  garage reloads from the local profile (test track, junkyard return).

Game hooks (Harmony): `OrderGenerator.Update` (prefix, generation only on the generator),
`OrderGenerator.GenerateNewJob` / `GenerateMission` (postfix, capture new orders),
`OrderGenerator.Load` (postfix, replace profile jobs with server state), `OrderGenerator.PrepareJob`
(postfix, job started on a car loader), `OrderGenerator.CancelJob` (prefix, block local-only removals),
`OrdersWindow.AcceptOrderAction` / `DeclineOrderAction` (prefix, ask the server first),
`GameScript.EndJob` + `GlobalData.AddPlayerMoney` / `AddPlayerExp` (capture payout and XP once),
`JobHelper.CheckJob` (postfix, detect progress), `CarLoader.LoadCar` (existing hook, fill `JobID`).

Packets: new `JobsState`, `OrderGeneratorRole`, `OrderGenerated`, `OrderAdded`, `OrderAction`,
`OrderActionResult`, `JobStarted`, `JobProgress`, `JobEndRequest`, `JobRemoved`; changed
`CarSpawnRequest`/`CarSpawnResponse` (`JobID` is now set and validated) and `StatsHooks` (job XP no
longer goes through `StatsAction`). New `PacketTypes` values are appended at the end of the enum.

## Capabilities

### New Capabilities
- `jobs-sync`: shared customer orders and jobs in a co-op session: one server-owned order list,
  exclusive accept, decline, expiry, customer car spawn, task progress, job completion with shared
  payout and XP, and the same orders on every client including late joiners.

### Modified Capabilities
None (no specs exist yet).

## Impact

- Core: `PacketTypes`, new `Network/Packets/JobPackets.cs`, new DTOs `ModJob`/`ModJobTask`/`ModJobPart`,
  `ModGameState.JobsState`.
- Server: new `Network/Handlers/JobHandlers.cs` and a jobs service ticked from `Server.Update`
  (expiry, claim timeout, generator election); `AuthHandlers.OnAskForSync` sends `JobsState`;
  `CarHandlers` validates job spawns; `Client.Disconnect` releases claims.
- Client: new `Logic/Jobs/` (state mirror, apply, hooks), `CarSpawnManager`, `CarHandlers`, `StatsHooks`.
- Harness: `tools/TestHarness/Features/JobsCommands.cs`, `StateDump` (`jobs` section, `orderConnection`),
  scenarios `jobs.ps1` and `jobs-latejoin.ps1`.
- Depends on `sync-car-parts` (part state of the customer car after `PrepareJob`, late-join car replay)
  and `sync-car-placement-and-lifts` (free car loader / placement); fluid levels checked by `EndJob`
  come from `sync-car-details`.
